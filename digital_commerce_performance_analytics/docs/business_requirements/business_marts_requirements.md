# Business Marts Requirements

## Project

Digital Commerce Performance Analytics

## Phase

Phase 6 — Business Marts

## Purpose

Define the approved consumers, business decisions, analytical questions, grains, and downstream use cases that govern the implemented Business Marts layer.

The Business Marts layer must consume governed Core Warehouse entities and must not reconstruct source, staging, sessionization, transaction-deduplication, or channel-classification logic.

## Approved Upstream Core Models

The Business Marts layer consumes the following governed Core Warehouse models:

- `dim_date`
- `dim_channel`
- `fct_sessions`
- `fct_transactions`

## Business Mart Design Principles

Business marts must:

- answer a defined business question
- serve a known analytical consumer
- expose a clear and documented grain
- use governed Core Warehouse models as upstream inputs
- reuse approved business definitions
- avoid duplicating transformation logic across marts
- minimize BI-side calculation complexity
- support stable downstream Power BI reporting
- remain reconcilable to the Core Warehouse
- avoid creating marts that do not have a clear analytical purpose

# P6C — Marketing / Channel Mart

## Primary Consumers

- Marketing analysts
- Growth analysts
- Commercial analysts
- Marketing managers
- Business stakeholders reviewing acquisition performance

## Primary Business Decisions

The mart should support decisions about:

- which acquisition channels generate the most traffic
- which channels generate purchasing sessions
- which channels generate the strongest commercial value
- which acquisition sources contribute to revenue
- where conversion performance is weak
- where marketing traffic produces low commercial return
- how channel performance changes over time

## Primary Business Questions

The mart should answer:

- How many sessions are generated by each channel?
- How many purchasing sessions are generated by each channel?
- What is the session conversion rate by channel?
- How many transactions are generated by each channel?
- How much purchase revenue is generated by each channel?
- What is average revenue per session by channel?
- What is average order value by channel?
- Which sources and mediums drive the strongest commercial results?
- How does channel performance change by date?
- What proportion of traffic is classified as Unknown or Other?

## Approved Grain

One row per:

`session_date + channel_key`

`session_date` uses the governed session date from `fct_sessions`.

Channel performance is governed at the channel-group level through `channel_key`; source-, medium-, and campaign-level breakdowns are not part of the implemented mart grain.

## Required Upstream Models

- `fct_sessions`
- `fct_transactions`
- `dim_channel`
- `dim_date`

## Required Measures

- session_count
- purchasing_session_count
- conversion_rate
- session_attributed_transaction_count
- session_attributed_purchase_revenue
- session_contribution
- purchasing_session_contribution
- transaction_contribution
- revenue_contribution

## Required Dimensions

- session date
- governed channel

# P6E - Customer Behavior Mart

## Primary Consumers

- Customer analysts
- Growth analysts
- Marketing analysts
- Commercial analysts

## Primary Business Decisions

The mart should support decisions about:

- pseudo-user engagement
- purchasing behavior
- repeated session activity
- repeated purchasing activity
- differences between purchasing and non-purchasing users
- pseudo-user-level commercial contribution

## Primary Business Questions

The mart should answer:

- How many unique pseudo-users are observed?
- How many pseudo-users generate purchasing sessions?
- How many sessions does each pseudo-user generate?
- On how many distinct dates is each pseudo-user observed?
- Which pseudo-users demonstrate repeated session activity?
- Which pseudo-users return on a later observed date?
- How many purchasing sessions does each pseudo-user generate?
- How many transactions does each pseudo-user generate?
- How much purchase revenue does each pseudo-user generate?
- Which pseudo-users generate purchasing activity across multiple sessions?
- Which pseudo-users generate purchasing activity across multiple dates?
- How does purchasing behavior differ from non-purchasing behavior?

## Approved Grain

One row per:

`user_pseudo_id`

The mart represents behavior across the governed observation window.

Optional downstream time-based variants may be introduced only when a separate business requirement justifies a different grain.

## Required Upstream Models

- `fct_sessions`
- `fct_transactions`

## Required Measures

- session_count
- active_date_count
- purchasing_session_count
- transaction_count
- purchase_revenue
- refund_value
- total_item_quantity
- first_observed_session_date
- last_observed_session_date
- first_observed_purchase_date
- last_observed_purchase_date
- observed_user_span_days
- purchasing_date_count

## Required Behavioral Attributes

- is_purchasing_user
- is_multi_session_user
- returned_on_later_date
- is_repeat_purchasing_session_user
- is_repeat_purchasing_date_user

## Behavioral Definitions

### Multi-Session User

A pseudo-user is a multi-session user when:

`session_count > 1`

This identifies repeated governed session activity within the observation window.

### Returned on a Later Date

A pseudo-user is considered to have returned on a later observed date when:

`active_date_count > 1`

This is intentionally distinct from `is_multi_session_user`, because multiple sessions may occur on the same date.

### Purchasing User

A pseudo-user is a purchasing user when:

`purchasing_session_count > 0`

### Repeat Purchasing Session User

A pseudo-user demonstrates repeat purchasing-session behavior when:

`purchasing_session_count > 1`

This definition identifies purchasing activity across multiple governed sessions.

It must not be inferred from `transaction_count > 1`, because a single purchasing session may contain multiple transactions.

### Repeat Purchasing Date User

A pseudo-user demonstrates repeat purchasing-date behavior when purchasing activity occurs on more than one distinct governed session date:

`purchasing_date_count > 1`

This is a stricter temporal definition than repeat purchasing-session behavior because multiple purchasing sessions may occur on the same date.

## Observation-Window Semantics

`first_observed_session_date` and `last_observed_session_date` represent the first and last governed session dates visible for the pseudo-user within the available dataset.

They must not be interpreted as the pseudo-user's true first-ever or last-ever interaction with the business.

Similarly, `first_observed_purchase_date` and `last_observed_purchase_date` represent the first and last purchasing-session dates visible within the governed observation window.

`observed_user_span_days` measures the number of calendar days between the first and last observed governed session dates.

## GA4 Session Number

`ga_session_number` may be used as a supporting behavioral or diagnostic attribute where required.

It must not be treated as authoritative customer identity or used by itself to establish a production-grade new-versus-returning customer classification.

Observed profiling shows that session-number values are not perfectly unique within every pseudo-user history.

## Important Limitation

`user_pseudo_id` is the available analytical user identifier.

Authenticated customer identity is not available in the source dataset.

Therefore, this mart represents observed GA4 pseudo-user behavior rather than a production-grade customer master.

Terms such as `customer`, `new customer`, and `returning customer` must not be inferred directly from `user_pseudo_id`, first-observed dates, or `ga_session_number`.

# P6F — Device / Geography Performance Mart

## Primary Consumers

- Marketing analysts

- Ecommerce analysts

- Product analysts

- Commercial analysts

- Business stakeholders reviewing market and device performance

## Primary Business Decisions

The mart should support decisions about:

- differences in ecommerce performance across device categories

- differences in ecommerce performance across countries

- device segments with weak conversion or commercial performance

- geographic markets generating strong or weak commercial outcomes

- whether segment-level performance differences are driven by traffic, conversion, or commercial value

- how device and country performance changes over time

## Primary Business Questions

The mart should answer:

- How many sessions are generated by each device category and country?

- How many purchasing sessions are generated by each device category and country?

- What is the session conversion rate by device category and country?

- How many transactions are attributed to each device and country segment?

- How much purchase revenue is attributed to each device and country segment?

- What is revenue per session by device category and country?

- Which device categories generate the strongest or weakest conversion performance?

- Which countries generate the strongest commercial performance?

- Are segment-level revenue differences driven primarily by traffic volume, conversion, or transaction activity?

- How does device and country performance change over time?

- What proportion of sessions cannot be assigned to a known country?

## Approved Grain

One row per:

`session_date + device_category + country`

`session_date` must use the governed session date from `fct_sessions`.

Raw GA4 `event_date` must not be used to reconstruct the mart grain because a governed session may span more than one raw event date.

## Approved Segmentation Dimensions

### Device Category

`device_category` is the approved device segmentation attribute.

Source profiling identified three observed device categories and no sessions with an invalid device category.

Device category is stable within the governed session population.

### Country

`country` is the approved geographic segmentation attribute.

Country is stable within the governed session population.

Missing, blank, or `(not set)` country values must remain part of the analytical population and must be represented as `Unknown` in the business mart rather than excluded.

This preserves reconciliation between the mart and the governed session population.

## Excluded Segmentation Dimensions

The following available GA4 attributes are not included in the current mart:

- operating system

- browser

- region

- city

Operating system and browser are excluded because no current business requirement justifies the additional segmentation complexity.

Region is not required for the primary mart grain.

City is excluded because source profiling identified substantial missing or invalid coverage.

These attributes may be introduced later only when a defined analytical consumer or business requirement justifies them.

## Required Upstream Models

- `fct_sessions`

- `dim_date`

The mart must consume governed session-level attributes and measures rather than reconstructing device, geography, session, or purchase attribution from raw GA4 events.

## Required Measures

- session_count

- purchasing_session_count

- conversion_rate

- transaction_count

- purchase_revenue

- revenue_per_session

## Attribution Semantics

Device and country are session-level attributes.

Commercial measures exposed by this mart must therefore use session-attributed commercial activity from `fct_sessions`.

Transactions and purchase revenue are attributed to the device category and country of their originating governed session and to that session's governed `session_date`.

The mart must not combine transaction-date commercial measures with session-date segmentation in the same KPI definition.

## Reconciliation Requirements

The mart must preserve the full governed session population, including sessions with unknown country.

Across all segment rows:

- `session_count` must reconcile to `fct_sessions`

- `purchasing_session_count` must reconcile to `fct_sessions`

- `transaction_count` must reconcile to session-attributed transaction counts in `fct_sessions`

- `purchase_revenue` must reconcile to session-attributed purchase revenue in `fct_sessions`

The approved governed session population is 360,129 sessions.

The validated analytical grain contains 17,052 observed combinations of:

`session_date + device_category + country`

within the current observation window.

# Cross-Mart Requirements

## Grain Control

Each mart must publish one explicit analytical grain.

Measures from different grains must not be combined without controlled aggregation.

## KPI Ownership

KPI formulas are governed by the approved P6B KPI contracts.

No mart may introduce a conflicting local KPI definition.

## Reconciliation

All mart-level additive measures must reconcile to the appropriate Core Warehouse fact.

## Source of Truth

Core Warehouse entities remain the source of truth for session and transaction populations.

Business marts provide purpose-specific analytical aggregations and must not replace core warehouse governance.

## BI Consumption

Business marts should reduce repeated transformation logic in Power BI and provide stable business-readable datasets for downstream serving and semantic layers.

## Phase 6 Implementation Sequence

The approved Phase 6 sequence is:

1. P6A — Define Mart Consumers
2. P6B — Define KPI Contracts
3. P6C — Marketing / Channel Mart
4. P6D — Ecommerce Performance Mart
5. P6E — Customer Behavior Mart
6. P6F — Device / Geography Mart
7. P6G — Mart Validation
8. P6H — Performance Optimization

# Reproduction Guide

## Purpose

This guide explains how to reproduce the analytics engineering environment for the Digital Commerce Performance Analytics project.

The workflow uses the public Google Analytics 4 ecommerce dataset in BigQuery, dbt Core for transformation and testing, and Power BI for the final reporting layer.

The repository does not contain raw source data, Google Cloud credentials, or machine-specific dbt profile files.

---

## 1. Prerequisites

The project was developed and validated with the following core environment:

- Python 3.11
- dbt Core 1.12.0
- dbt BigQuery adapter 1.12.0
- Google Cloud / BigQuery access
- Git
- Power BI Desktop for the reporting layer

The validated Python environment used Python 3.11.9.

The Python dependency required by the analytics engineering layer is pinned in the root `requirements.txt` file:

    dbt-bigquery==1.12.0

Installing `dbt-bigquery` also installs the compatible dbt Core dependencies required by the adapter.

---

## 2. Clone the Repository

Clone the repository and move into the project root:

    git clone <repository-url>
    cd digital-commerce-performance-analytics

The dbt project itself is located in:

    digital_commerce_performance_analytics/

All environment and dependency commands in the following sections should initially be run from the repository root unless otherwise stated.

---

## 3. Create a Python Virtual Environment

Create a local virtual environment:

### Windows PowerShell

    python -m venv .venv
    .\.venv\Scripts\Activate.ps1

### macOS / Linux

    python3 -m venv .venv
    source .venv/bin/activate

Install the project dependency:

    pip install -r requirements.txt

Confirm the installation:

    python --version
    dbt --version

The validated project environment used:

    Python 3.11.9
    dbt-core 1.12.0
    dbt-bigquery 1.12.0

Patch-version updates may become available after the project release. The versions above represent the environment used for the validated project build.

---

## 4. Google Cloud and BigQuery Access

The project reads from the public GA4 ecommerce sample dataset:

    bigquery-public-data.ga4_obfuscated_sample_ecommerce

The approved analytical source window is:

    2020-11-01 through 2021-01-31

The source dataset is located in the BigQuery `US` location.

A Google Cloud project with BigQuery access is required to execute the dbt models and create the development datasets generated by the project.

The development environment used during implementation was configured with:

    project: digital-commerce-analytics
    dataset: analytics_dev
    location: US

These values are not credentials. A reproducing user may use their own Google Cloud project and development dataset instead.

---

## 5. Configure dbt Authentication

The validated development environment uses the BigQuery adapter with OAuth authentication.

dbt Core reads connection configuration from a local `profiles.yml` file. This file is intentionally not stored in the repository because connection configuration is machine-specific and may contain sensitive information in other authentication setups.

The default dbt profile directory is typically:

### Windows

    C:\Users\<username>\.dbt\profiles.yml

### macOS / Linux

    ~/.dbt/profiles.yml

Create a profile named `digital_commerce_performance_analytics`.

A minimal OAuth configuration is:

    digital_commerce_performance_analytics:
      outputs:
        dev:
          type: bigquery
          method: oauth
          project: <your-gcp-project-id>
          dataset: <your-development-dataset>
          location: US
          threads: 4
          priority: interactive
      target: dev

Replace:

- `<your-gcp-project-id>` with the Google Cloud project used to execute the project.
- `<your-development-dataset>` with the BigQuery dataset used for dbt development objects.

The profile name must match the profile configured in:

    digital_commerce_performance_analytics/dbt_project.yml

which is:

    profile: 'digital_commerce_performance_analytics'

No service-account key or other credential file should be committed to the repository.

---

## 6. Verify the dbt Connection

Move into the dbt project directory:

    cd digital_commerce_performance_analytics

Verify the project configuration and BigQuery connection:

    dbt debug

A successful debug confirms that dbt can locate the project and profile and connect to BigQuery.

If authentication is required, complete the Google OAuth authentication flow for the local environment before continuing.

---

## 7. Install dbt Dependencies

From the dbt project directory, run:

    dbt deps

This prepares any dbt package dependencies defined by the project.

Generated dependency directories such as `dbt_packages/` are local build artifacts and are intentionally excluded from version control.

---

## 8. Build and Validate the dbt Project

Run the complete project quality gate:

    dbt build

`dbt build` executes the project's models and associated data tests in dependency order.

At the final Phase 11 validation gate, the project produced:

- 13 table models
- 8 view models
- 363 data tests
- 384 successful dbt resources in total
- 0 warnings
- 0 errors
- 0 skipped resources

The expected final result for the validated project state was:

    PASS=384
    WARN=0
    ERROR=0
    SKIP=0
    TOTAL=384

Exact execution output may differ if the source dataset, project code, dbt version, or validation scope changes.

---

## 9. Analytical Model Flow

The dbt build creates the analytical layers in the following order:

    GA4 Public Ecommerce Source
        ↓
    Staging
        ↓
    Intermediate GA4 Entities
        ↓
    Core Warehouse
        ↓
    Business Marts
        ↓
    Executive KPI Layer
        ↓
    BI Serving Layer

The principal model groups are:

### Staging

    stg_ga4__events
    stg_ga4__items

### Intermediate

    int_ga4__session_events
    int_ga4__sessions
    int_ga4__transactions

### Core Warehouse

    dim_date
    dim_channel
    fct_sessions
    fct_transactions

### Business Marts

    mart_channel_daily
    mart_ecommerce_daily
    mart_segment_daily
    mart_user_behavior

### Executive KPI Layer

    executive_kpi_daily
    executive_kpi_trends_daily
    executive_channel_drivers_daily

### BI Serving Layer

    bi_executive_daily
    bi_channel_daily
    bi_commerce_daily
    bi_segment_daily
    bi_user_behavior

The serving layer provides the governed analytical interface used by the Power BI semantic model.

## 10. Validation Evidence

Validation is implemented at several levels rather than relying only on model execution.

Automated dbt tests cover areas including:

- source-to-staging reconciliation
- session and transaction integrity
- grain and uniqueness constraints
- core warehouse reconciliation
- business mart reconciliation
- KPI consistency
- BI serving reconciliation

Additional SQL validation and phase-level evidence are stored under:

    validation/

The consolidated validation documentation is available in:

    validation/README.md

The final end-to-end validation evidence is documented in:

    validation/reports/phase11_validation_summary.md

## 11. Power BI Reporting Layer

The canonical Power BI report is:

    power_bi/digital_commerce_performance_analytics.pbix

The report consumes the governed BI serving layer rather than rebuilding business definitions independently inside the presentation layer.

The final report contains four analytical pages:

1. Executive Overview
2. Acquisition & Channel Performance
3. Commerce Performance
4. Customer Behaviour & Segmentation

Supporting semantic-model and report documentation is stored under:

    power_bi/documentation/

Final report screenshots of the four final report pages are stored under:

    power_bi/assets/

Power BI Desktop is required to open and interact with the `.pbix` file.

A reproducing user connecting the report to a different BigQuery project or dataset may need to update the Power BI data-source connection settings to match their environment.

## 13. Local and Generated Artifacts

The following types of artifacts are intentionally excluded from version control where applicable:

- `.venv/`
- dbt `target/`
- dbt `logs/`
- `dbt_packages/`
- local environment configuration
- machine-specific dbt profiles
- credentials
- raw source data

The repository is designed to preserve transformation logic, tests, documentation, validation evidence, BI assets, and reproducible dependency configuration without committing local runtime artifacts or secrets.

---

## 14. Reproduction Checklist

A successful reproduction should complete the following sequence:

    Clone repository
        ↓
    Create and activate Python virtual environment
        ↓
    Install requirements
        ↓
    Configure Google Cloud / BigQuery access
        ↓
    Create local dbt profiles.yml
        ↓
    Run dbt debug
        ↓
    Run dbt deps
        ↓
    Run dbt build
        ↓
    Review validation evidence
        ↓
    Open or reconnect the Power BI report

The dbt build should complete without errors before downstream analytical results are treated as validated.
